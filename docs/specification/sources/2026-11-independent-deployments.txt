You do not need to separate GLAM Beauty into different GitHub repositories. In fact, for your business, I recommend keeping the website, mobile app and backend in one repository (a monorepo) while deploying them as separate applications.

This is how companies can maintain a website and mobile applications that share users, products, orders and business logic without maintaining three completely different systems.

The important distinction is that one repository does not mean one deployment.

The website and backend can run as separate Railway services, while the iOS and Android applications are built into native applications and distributed through the Apple App Store and Google Play.

## 3. How each application gets launched

| Component       | Deployment destination                            | Public address                             |
| --------------- | ------------------------------------------------- | ------------------------------------------ |
| Website         | Railway web service                               | `www.glam.beauty`                          |
| Backend API     | Railway API service                               | `api.glam.beauty`                          |
| iOS app         | Apple App Store                                   | GLAM Beauty                                |
| Android app     | Google Play                                       | GLAM Beauty                                |
| Database        | Supabase                                          | Shared, not publicly exposed as a database |
| Admin dashboard | Railway web/admin service or protected web routes | `admin.glam.beauty` if separated           |

The mobile apps do not need Railway hosting for their native user interfaces. They call the backend over HTTPS, just as the website does.

The same customer can register on the website, install the mobile app and sign in with the same phone number. Their Style Passport, saved looks, wardrobe, orders and bookings will be available on both platforms.

## 4. How updates work after launch

1. Website update

   Codex updates the web application. Railway rebuilds and deploys the web service. Users see the new version when they visit the site.

2. Backend update

   Codex updates the API. Railway deploys the backend independently. Both web and mobile clients can use the updated API, provided compatibility is maintained.

3. Mobile app update

   Codex updates the React Native/Expo app. You create new iOS and Android builds for store submission. Eligible JavaScript and asset updates may be delivered over the air through Expo Updates, subject to runtime compatibility and store policies.

4. Database update

   A controlled Supabase migration updates the shared database. Both website and mobile clients use the updated structures without requiring separate databases.

A crucial rule: because app-store updates can take time, backend changes must remain compatible with older mobile versions. Otherwise, a Railway API deployment could break users who have not yet updated their apps.

Keep one repository, two Railway services (web and API), two mobile store builds (iOS and Android), and one Supabase production backend. Add a separate admin deployment only if there is a genuine security or operational reason; protected admin routes can also work.
