# GLAM Beauty — Master Mobile Screen Inventory and Monorepo Architecture

Scope: 208 original GL screens + 14 AI Transformation screens (TP-01–TP-14) + Consumer Home.

This is the proposed canonical product and engineering handover for Claude Design and Codex. It preserves the full mobile functionality discussed so far while requiring the mobile app and web platform to operate from one monorepo, one shared Supabase project, one identity system and one set of business rules.

The important distinction is that one backend does not mean one user interface. The mobile app must be built as a genuine Flutter application; the website and business dashboards retain their own web-native interfaces.

## 1. Target monorepo architecture

GLAM Beauty Monorepo

One Git repository · Coordinated releases

Flutter Mobile

iOS / Android · Native-first UX

React Web

Consumer web · Merchant · Admin

Shared API and Business Logic

Auth · AI orchestration · Commerce · Bookings · Payments · Credits · Roles

Shared Supabase

PostgreSQL · Auth · Storage · RLS · Realtime · Edge Functions

### Non-negotiable shared-backend rules

- One production Supabase project: Web and mobile use the same production identity, records, products, bookings, credits and transactions.
- Separate development and production environments: Never test destructive migrations or payment flows against production.
- One migration history: Supabase migrations are maintained centrally in the monorepo, not independently in web and mobile.
- One user identity: A user can sign in on web and mobile and access the same account.
- Server-enforced roles: Consumer, Creator, Merchant, Professional, Advertiser, Affiliate and Admin permissions must be enforced by RLS and backend authorization.
- One financial ledger: Purchases, subscriptions, credits, commissions, refunds and payouts must be calculated and reconciled server-side.
- One AI transformation record: Analysis, generated looks, tutorials and saved plans must be retrievable from both clients, subject to permissions.
- No duplicate business logic: Flutter and React can have different UI implementations, but must use the same authoritative pricing, entitlements, order and booking rules.
