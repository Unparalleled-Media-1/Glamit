# GLAM AI — SUPABASE DATABASE CREATION, MIGRATION & APPLICATION INTEGRATION

## OBJECTIVE

Begin implementing the complete production-oriented PostgreSQL database architecture for GLAM AI using the Supabase project already connected to this development environment.

GLAM AI operates under Zanzu Technologies Inc., a US-based company.

The application combines:

* AI-powered beauty, face, hair and color analysis

* AI makeup and hairstyle transformations

* AI Personal Stylist and conversational advisor

* Fashion styling, outfit recommendations and virtual try-on

* Weather-, destination- and occasion-based styling

* Digital wardrobe and Style Passport

* Beauty, cosmetics, haircare, fashion and accessories marketplace

* Multi-merchant shopping and checkout

* Salons, hairstylists, makeup artists, tailors and other professionals

* Professional appointment bookings

* Merchant and creator dashboards

* Geo-targeted advertising and sponsored placements

* Stripe Connect marketplace payments

* A 10% GLAM AI commission on eligible physical-product sales

* International merchants, currencies, languages and delivery destinations

* Organization-scoped admin dashboards and platform operations

The goal is to establish a reliable, secure and extensible database foundation that supports the existing web and mobile application without breaking completed functionality.

## PHASE 0 — MANDATORY PRE-MIGRATION AUDIT

Before creating or modifying any tables:

1. Inspect the entire repository and all existing branches.

2. Identify the canonical application architecture and current database configuration.

3. Identify all existing SQL migrations, Prisma schemas, ORM models, API contracts and Supabase references.

4. Inventory every implemented and planned feature that requires persistent data.

5. Identify duplicate tables, inconsistent naming, missing relationships and conflicting database implementations.

6. Check whether the connected Supabase project already contains tables, functions, policies, storage buckets or data.

7. Identify whether this is a development, staging or production project.

8. Confirm that the project connection has the required migration permissions.

9. Verify that the working branch is up to date with main and that required feature branches have been reviewed and merged.

10. Do not force-push, overwrite unrelated changes or delete existing data.

Produce DATABASE_PRE_MIGRATION_AUDIT.md.

If the connected project is production or contains valuable existing data, stop before applying migrations and request approval.

## PHASE 2 — MIGRATIONS

Generate version-controlled Supabase SQL migrations.

Requirements:

1. Every schema change must be reproducible from a clean database.

2. All primary keys, foreign keys, constraints and indexes must be defined.

3. Use appropriate unique constraints and check constraints.

4. Use consistent timestamps and timezone handling.

5. Use explicit database relationships.

6. Create necessary indexes for frequent queries.

7. Avoid unnecessary JSON fields where relational structures are appropriate.

8. Use PostGIS only if geographic query requirements justify it and the extension is supported.

9. Use pgvector only if vector retrieval is needed and supported.

10. Never use destructive DROP or TRUNCATE operations without explicit approval.

11. Never silently overwrite existing tables or policies.

12. Keep migration history synchronized with the repository.

Produce a documented migration manifest.

## PHASE 3 — ROW LEVEL SECURITY

Enable and validate RLS on all application tables exposed through Supabase APIs.

Enforce:

* Consumers can access only their own private records.

* Merchants can manage only their own authorized catalogue and orders.

* Professionals can access only their own appointments and business data.

* Advertisers can manage only campaigns belonging to their organizations.

* Creators can manage only their own storefronts and content.

* Financial records cannot be modified directly by ordinary clients.

* Admin privileges must be verified server-side.

* Service-role access must never be exposed to client applications.

Create automated tests for unauthorized cross-user and cross-organization access.

A table must not be considered ready merely because RLS is enabled; its policies must be tested.

## PHASE 4 — STORAGE

Create appropriate private and public Supabase Storage buckets for:

* User profile images

* Digital wardrobe images

* Merchant product images

* Professional portfolios

* Creator content

* Advertising creatives

* Verification documents

Apply file type restrictions, size limits, access policies and retention controls.

Verification documents and private facial imagery must not be publicly accessible.

## PHASE 5 — APPLY TO CONNECTED SUPABASE

After the pre-migration audit and migration validation:

1. Confirm the connected Supabase project reference.

2. Confirm the target environment is authorized for development migrations.

3. Back up any existing schema and valuable data.

4. Validate migrations against a disposable local or test database.

5. Apply migrations to the connected development Supabase project in controlled batches.

6. Verify every table, foreign key, index, policy and storage bucket.

7. Run integration and security tests.

8. Report actual migration results.

Do not claim deployment success unless Supabase confirms successful execution.

If credentials, network permissions or database migration access are missing, stop and report the exact blocker.

Never ask for database passwords or API keys in chat or commit them to Git.
