## Data and consistency conventions

UUID primary keys, explicit FKs to canonical owner/org entities, timestamptz UTC storage, immutable created_at and server-controlled updates/version fields. Use relational links for ownership, variant selection, line allocations, membership and bookings. JSON is justified only for versioned provider-specific estimates/metadata and existing immutable component contracts; never embed secrets, payment-card data or opaque org authorization.

Unique constraints: issuer+subject; org+user; owner+idempotency key; provider+event ID; listing+variant+revision; order+merchant; journal+business key. Index tenant/owner+created_at, org+status, eligible offer region/currency/freshness, pending jobs/outbox and foreign keys used in policies. Check quantity/stock nonnegative, exact money currency and valid state transitions. Signed server commands govern publication, consent and fulfillment; immutable facts may only be compensated with new records.

Supabase Auth is the identity provider through existing RS256/ES256 verification; do not add passwords or accept a service-role key as an end-user session. Keep private operations behind existing authenticated APIs. Qualified mapping from Supabase subject to app_user is required before any direct-client RLS design. Commercial and booking transactions reserve stock/slots atomically and snapshot authoritative prices/terms; processing work is queued through outbox, not inside DB locks.

Storage keeps large private media out of PostgreSQL. No PostGIS/pgvector until a measured query need and target extension support are established; use country/region/city and bounded coordinates/radius first. Multi-currency amounts are minor-unit integers with verified currency exponent; FX conversions need quoted rate/source/time and may not reuse a two-decimal assumption. Language identifiers, local venue time zone and user-selected destination are explicit. No inference of protected traits, religion, medical diagnosis or attractiveness scores.
