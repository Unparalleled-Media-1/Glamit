## What it creates
`professional_service`, `availability_rule`, `booking` (all RLS-enabled, no client-role grants) and one exclusion constraint `booking_no_overlap_when_held` so two accepted/completed bookings of one organization can never overlap. Requests hold no time; accepting does.

## Risks and decisions needed
* **Extension:** the SQL runs `CREATE EXTENSION IF NOT EXISTS btree_gist` (required for uuid equality inside a GiST exclusion). It is a standard contrib extension on Supabase, but creating an extension is a database-level change; confirm the migration role may do so, or pre-create it.
* **Rollback:** the downgrade refuses to run unless all three tables are empty (same rule as 0018). After real bookings exist the recovery path is forward-fix.
* **Runtime role:** `runtime_role_proposal.sql` now also grants the API role SELECT/INSERT/DELETE on `availability_rule`, SELECT/INSERT/UPDATE on `booking` and `professional_service`. Apply it only after 0019.
* **Readiness:** the API treats 0019 as a current head but does not require it; booking routes simply fail until the tables exist. Do not enable any booking UI before 0019 is applied.
* No payments, deposits or provider calendars are involved; no personal data beyond the booking client's account id and a 500-character note.
